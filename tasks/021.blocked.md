# Task 021 blocked: video execution policy cannot be enforced as specified

The brief requires a video-mode seccomp profile that allows `execve` of
"exactly the configured ffmpeg path", with confinement installed before any
ffmpeg or ffprobe subprocess starts. This pathname restriction cannot be
implemented by the host's seccomp BPF filters: filters receive syscall argument
values, including pointer addresses, but cannot dereference the pathname
pointer. Comparing a pointer value does not authorize the executable named by
the bytes at that address.

This is a security-contract blocker, rather than a missing dependency or
manifest entry. Merely allowing `execve` would not provide the stated guarantee.

## Evidence

- `tasks/021-zip-and-video.md`, Design / Video, requires the pathname-specific
  seccomp exception and prohibits starting the subprocess before confinement.
- `crates/yhotos-codec-host/src/seccomp.rs` uses `seccompiler` BPF filters. The
  existing policy denies exec and process creation, permitting only inspected
  pthread clone flags.
- `crates/yhotos-codec-host/README.md` explicitly documents that BPF cannot
  inspect path pointers safely.
- `crates/yhotos-codec-host/src/filesystem.rs` handles all Landlock filesystem
  rights but grants no execute rights. Its current read permissions cover only
  the input file and output directory; a dynamically linked subprocess also
  needs an explicit runtime-file policy.
- `docs/threat-model.md` section 4.1 requires no exec inside the codec sandbox.
  The task needs a documented video exception and an enforceable replacement
  policy. Agents may not edit the binding docs to match an implementation.
- The Linux kernel documentation confirms that seccomp BPF cannot dereference
  pointers: <https://docs.kernel.org/userspace-api/seccomp_filter.html>.

## Decision needed to resume

Revise the brief and binding security documentation to specify which mechanism
enforces each part of the video policy. A possible design uses seccomp for the
syscall allow list and Landlock for executable-file authorization, installed
before any subprocess starts. Landlock supports filesystem execute rules:
<https://docs.kernel.org/userspace-api/landlock.html>.

The revised design should explicitly cover both ffmpeg and ffprobe, their
required read-only loader/library files, bounded subprocess creation, inherited
resource limits and confinement, and termination of all descendants on timeout.
Keep the image-mode no-exec policy intact. Tests must prove that an unrelated
executable and writable output files cannot be executed, in addition to the
required network and filesystem denial tests.
