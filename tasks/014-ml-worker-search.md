# 014 ML worker and search

## Goal

A GPU worker (`ml/`) consumes `MlEmbed`, `MlFaces`, `MlOcr`, `MlTags` jobs and writes embeddings, face boxes and clusters, OCR text, and auto-tags to Postgres; the public `/search` page and `/api/v1/search` combine semantic, text, tag and structured filters with reciprocal rank fusion and visibility filtering; faces and person search are admin-only. This is the Immich-grade search from `docs/scope.md` 5.5, built so the request path never waits on a model except for the single query embedding call.

## Design

### ML service (`ml/`)
- Runs as a job consumer against Postgres (role `yhotos_worker`), using the same `jobs` table protocol as the Rust worker (claim query from architecture section 7, implemented in Python with `psycopg` 3; `LISTEN jobs`). It handles only the `Ml*` kinds.
- Models (ONNX, pinned by SHA-256 in `ml/models.lock`; downloaded at image build, never at runtime; the container has no egress): embeddings `SigLIP` (`ViT-B/16`, 768-d; fall back to `CLIP ViT-L/14` if SigLIP export is unavailable; record which in the PR), faces OpenCV Zoo `YuNet` detector and `SFace` recogniser (128-d; see docs/decisions.md, which replaced InsightFace buffalo_l), OCR `RapidOCR` (PP-OCRv4 det+rec), tags from the embedding model with a curated label list (`ml/labels.txt`, ~600 scene/object labels, zero-shot, threshold 0.25, max 12 per photo).
- Input: the photo's `large` JPEG derivative (never the original) read from `/data` mounted read-only.
- Output to Postgres in one transaction per job: `embeddings` row, `faces` rows with bbox normalized to [0,1], embedding, quality score; `ocr_text` with `tsv` generated by a trigger; `photo_tags` with `source = auto`, `confidence`. Idempotent: re-running replaces that photo's rows for that model version (`model` column carries name+version).
- Face clustering: `MlFaces` writes faces unassigned; a separate `MlCluster` job (enqueued by the admin "Rebuild people" action and nightly) runs DBSCAN-like clustering over all unassigned face embeddings (cosine, eps 0.6, min 2) and creates or extends `persons`, never merging two named persons automatically.
- Query embedding: HTTP `POST /embed-text` on the internal network, body `{text}`, 20 ms budget on GPU, returns the vector; `yhotos-http` calls it with a 100 ms timeout and degrades to text-only search on failure (logged, metric incremented).
- All strings from models (OCR text, labels) are treated as untrusted: length-capped (OCR 4 KB per photo), control characters stripped, stored as text, escaped on output.
- Tests: `pytest` with a tiny fixture set; model outputs are asserted by shape and determinism, not exact values; the job protocol is tested against a real Postgres in the compose stack; an "evil OCR" fixture with `<script>` text verifies escaping end to end (HTTP test in Rust).

### Search (`yhotos-http`)
- Parser (`search/query.rs`): free text plus filters `camera:`, `lens:`, `tag:`, `place:`, `year:`, `month:`, `color:` (hex or name), `is:raw|hdr|video`, `before:`/`after:` dates, quoted phrases. Bounded: 256 chars, 16 terms, 8 filters. Fuzzed (`fuzz/fuzz_targets/search_query.rs`).
- Execution: up to three candidate lists, each limited to 200: semantic (`embeddings <=> $q` HNSW), text (`ocr_text.tsv @@ plainto_tsquery` plus `photos.title` trigram via `pg_trgm`), tag/structured (SQL filters). Fused with reciprocal rank fusion (k = 60), then visibility-filtered with the SQL fragment from task 011, paginated 60 per page. Structured filters apply to all lists. Single round trip per list; lists run concurrently.
- Admin-only person search (`person:` filter and `/admin/people`) lives on the admin router; the public parser rejects `person:` as an unknown filter (treated as text).
- `/search` page renders the grid from task 011 with the query box, active filters as chips, and "more like this" links on photo pages (`/search?like=<short_id>`, semantic neighbors of that photo's embedding, visibility filtered).
- Typeahead: `/api/v1/suggest?q=` returns tags, places, cameras, lenses matching a prefix (visibility-aware counts), rate limited `cheap`.
- Results cache: none at the edge (private by principal); in-process query-embedding cache (moka, 1k entries, 10 min) keyed by normalized text.

### Admin people UI (feature `admin`)
`/admin/people`: clusters with sample faces, name/merge/hide, "Rebuild people". Face thumbnails are cropped on the fly from the `medium` derivative by the codec host into a `face` variant (cached derivative) so no face crops exist for public photos unless an admin opens this page.

### Tests (Rust)
Query parser table tests and fuzz; RRF ordering unit test; visibility: a restricted photo never appears in any list for anonymous (test seeds embeddings directly); `person:` ignored publicly; ML service down → text-only results and a 200; suggest rate limited; OCR `<script>` escaped in HTML and JSON.

### Bench
`search.rs`: fused search over 10k synthetic photos with random embeddings in the dev Postgres: p99 < 50 ms. Record `EXPLAIN` showing HNSW index use.

## Security notes

- B6: every model output is data. Caps, stripping, escaping, and the public/admin split are the controls; map each to a test.
- 4.8: faces admin-only; no face crops for public viewers; `persons.hidden` respected everywhere.
- The ML container: non-root, read-only root fs, `/data` read-only, no egress (`internal: true` network plus the Postgres link), GPU only.
- Python dependencies pinned with hashes; `pip-audit` in the ML `make check`.
- Allowed new Rust dependencies: `moka` (if not present), `pg_trgm` is a Postgres extension (migration in this task). Python: `onnxruntime-gpu`, `psycopg[binary]`, `numpy`, `pillow`, `rapidocr-onnxruntime`, YuNet and SFace ONNX files loaded directly with onnxruntime, `fastapi`+`uvicorn` for the embed endpoint.

## Performance

- Search budget as above. ML never in the request path except `/embed-text`.
- Queue priority for `Ml*` below `Ingest` so uploads never wait behind a backlog.
