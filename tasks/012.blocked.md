# Task 012 blocked: missing storage and codec prerequisites

Task: `tasks/012-upload.md`

No upload implementation was added. `AGENTS.md` explicitly identifies a missing
prerequisite crate API as a reason to write this report and stop. The core upload
flow cannot meet the brief's storage and validation requirements through the
existing APIs in the permitted crates.

## 1. Persistent temporary uploads cannot be reopened through storage

The brief requires `uploads.tmp_path` to contain only a directory id, and all paths
derived from database text must go through the storage layer's safe-join.

Existing interfaces:

- `crates/yhotos-storage/src/lib.rs:303`: `Store::tmp_dir()` creates a new directory.
- `crates/yhotos-storage/src/temp.rs:19`: `TempDir::path()` exposes its trusted path.
- `crates/yhotos-storage/src/temp.rs:25`: `TempDir::keep()` retains that directory
  but returns only a `PathBuf`.
- `crates/yhotos-storage/src/paths.rs:59`: `safe_join` is crate-private.
- `Store::open_read` and `Store::remove` accept only originals, derivatives and
  video keys; there is no temporary-directory lookup or removal by id.

After a server restart, PATCH and DELETE cannot recover a retained upload from
its stored directory id using the storage API. The expiry worker has the same
problem. Constructing `data_dir/tmp/<database value>` in HTTP or pipeline code
would violate the safe-join rule. Keeping paths or handles only in server memory
would not provide durable resumption or cleanup by a separate worker.

Required prerequisite: a storage-owned typed temporary-directory id and APIs to
create/open its upload file, reopen the retained directory and remove it by id,
with traversal and symlink checks performed inside `yhotos-storage`.

## 2. The codec host does not offer header-only identity requests

The brief explicitly requires `want: ["identity"]`, `outputs: []` to perform
header-only validation in the codec host.

In `crates/yhotos-codec-host/src/main.rs:318-322`, every job calls `identify` and
then unconditionally calls `decode`. `want` controls fields in the report but
does not skip the pixel pipeline. Calling the current host therefore performs
the full decode before the final PATCH can return, contrary to the required
header-only validation flow. Calling `yhotos-codec::identify` directly from the
server would violate the process boundary.

Required prerequisite: a host path that returns identity without calling decode
when no requested output or report field needs pixels, with a regression test
proving that identity-only requests do not decode.

## 3. The required MP4/MOV identity is unavailable

The upload allow list includes MP4/MOV and requires kind and dimensions from the
codec host. `yhotos-codec::Kind` in `crates/yhotos-codec/src/lib.rs:95-114` has only
still-image, RAW and unknown variants. The `ftyp` branch in
`crates/yhotos-codec/src/headers.rs:53-72` recognizes CR3, AVIF and HEIF brands and
rejects other brands, including ordinary MP4/MOV brands. The pipeline's
host-report kind also has no video variant.

Sniffing `ftyp` in `validate.rs` alone cannot supply the missing sandboxed video
identity or decoder agreement. Video transcoding is not needed to unblock this,
but bounded video identification is.

Required prerequisite: sandboxed MP4/MOV identity and a corresponding report kind,
or an explicit maintainer revision of the upload format requirements.

## Scope decision

The missing behavior is in `yhotos-storage`, `yhotos-codec-host` and
`yhotos-codec`, outside task 012's listed implementation areas. This is a
prerequisite API change, rather than a module declaration, manifest line, router
connection or benchmark target. Land the prerequisites or explicitly extend the
brief to cover those crate changes, then rerun task 012.

The five-original Tailscale walkthrough is also unverified: this worktree has no
`fixtures/large/originals` directory. That is a separate acceptance limitation,
not the reason implementation stopped.
